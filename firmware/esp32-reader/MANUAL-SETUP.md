# تركيب وتشغيل واختبار قارئ حضور RC522 مع شاشتي LCD

المنصة الفعلية: https://attendance-system-joe-2026.vercel.app/

هذه الخطوات خاصة بـESP32 DevKit الكلاسيكي وRC522 وكروت MIFARE 13.56MHz. لا تستخدم كروت RDM6300 ذات 125kHz. أسماء GPIO المكتوبة أهم من مكان الأرجل على البوردة. افصل USB قبل تغيير التوصيلات، وبعد التجربة استخدم مصدر 5V ثابت لتغذية ESP32 عبر USB. الكمبيوتر مطلوب للبرمجة فقط.

## 1. توصيل RC522 في كل فرع

| طرف RC522 | طرف ESP32 |
|---|---|
| 3.3V | 3V3، **ليس 5V** |
| GND | GND |
| SDA / SS | GPIO21 |
| SCK | GPIO18 |
| MOSI | GPIO23 |
| MISO | GPIO19 |
| RST | GPIO22 |
| IRQ | بدون توصيل |

طرف SDA على RC522 هنا هو SPI chip select؛ توصيله مختلف عن SDA شاشة I²C. الأسلاك قصيرة، والأرضي مشترك. هذا الربط يعتمد على [توثيق مكتبة القارئ](https://github.com/miguelbalboa/rfid#pin-layout) و[بيانات MFRC522](https://www.nxp.com/docs/en/data-sheet/MFRC522.pdf).

## 2. الاختيار الأول: LCD 16×2 مع I²C

الكود يدعم لوحة PCF8574 الشائعة: P0=RS، P1=RW، P2=E، P3=Backlight، P4–7=D4–7. العنوان الافتراضي `0x27`. بعض اللوحات عنوانها `0x3F` أو توزيع أرجلها مختلف؛ عدّل `LCD_I2C_ADDRESS` أو `display.h` حسب اللوحة الفعلية. لو الشاشة تعرض مربعات اضبط مقاومة التباين الصغيرة.

**لو لوحة الشاشة تعمل على 5V: استخدم محوّل مستويات I²C ثنائي الاتجاه BSS138 بين ESP32 والشاشة. لا توصل إشارات I²C المسحوبة إلى 5V مباشرة بأرجل ESP32.** تغذية PCF8574 ذات 5V وتوصيل 3.3V مباشرة أيضًا قد لا تحقق مستوى HIGH المطلوب. [بيانات PCF8574](https://www.nxp.com/docs/en/data-sheet/PCF8574_PCF8574A.pdf).

| التوصيل | الأطراف |
|---|---|
| تغذية الشاشة | VCC→5V/VIN الخارج من تغذية USB بحسب البوردة، GND→GND |
| مرجع المحوّل | LV→3V3، HV→5V، GND→GND |
| SDA | GPIO16→LV1؛ HV1→SDA الشاشة |
| SCL | GPIO17→LV2؛ HV2→SCL الشاشة |

المحوّل يحتاج pull-ups على الجانبين؛ أغلب وحدات BSS138 الجاهزة تحتويها. لا تجمع تغذية USB مع مصدر 5V خارجي مستقل على نفس البوردة. يمكن تشغيل اللوحة بمصدر USB واحد مناسب لكل المجموعة.

اختيار الكود: بيئة PlatformIO `esp32dev` أو `LCD_MODE=1`.

## 3. الاختيار الثاني: LCD 16×2 عادية، 16 طرفًا

الكود يعمل بوضع 4-bit، ولا يقرأ بيانات من الشاشة؛ **RW مثبت على GND**. التوصيل الآتي هو ترتيب HD44780 المعتاد، راجع الأسماء المطبوعة على الشاشة لأن ترقيم بعض الوحدات يختلف.

| طرف الشاشة | التوصيل |
|---|---|
| 1 VSS | GND |
| 2 VDD | 5V |
| 3 VO | وسط potentiometer 10kΩ؛ الطرفان الآخران 5V وGND |
| 4 RS | إشارة GPIO16 عبر محوّل المستوى الموضح أدناه |
| 5 RW | GND |
| 6 E | إشارة GPIO17 عبر المحوّل |
| 7–10 D0–D3 | بدون توصيل |
| 11 D4 | إشارة GPIO25 عبر المحوّل |
| 12 D5 | إشارة GPIO26 عبر المحوّل |
| 13 D6 | إشارة GPIO27 عبر المحوّل |
| 14 D7 | إشارة GPIO32 عبر المحوّل |
| 15 A / LED+ | 5V عبر مقاومة مناسبة؛ 220Ω نقطة بداية إذا لا توجد مقاومة على الوحدة |
| 16 K / LED− | GND |

لضمان مستويات الإشارة مع شاشة 5V استخدم **SN74HCT245**: يدعم HIGH من 3.3V ويخرج 5V. لا تستبدله عشوائيًا بـ74HC245 لأن عتبات الإدخال مختلفة. [بيانات TI](https://www.ti.com/lit/ds/symlink/sn74hct245.pdf).

توصيله لحزمة DIP20: pin20→5V، pin10→GND، pin1 DIR→5V، pin19 /OE→GND، ومكثف 100nF بين 20 و10. GPIO16/17/25/26/27/32→A1–A6 (pins2–7)، ثم B1–B6 (pins18–13)→RS/E/D4/D5/D6/D7 بنفس الترتيب. اربط A7 وA8 غير المستخدمين بـGND، واترك B7 وB8 بدون توصيل.

اختيار الكود: بيئة `esp32-parallel` أو `LCD_MODE=2`. **لا توصل الشاشتين معًا على نفس ESP32 بهذا التوزيع**؛ الأرجل 16 و17 مشتركة بين الاختيارين. يمكن استخدام I²C في فرع والعادية في الفرع الآخر.

شاشات HD44780 المعتادة لا تعرض الأسماء العربية كاملة. الشاشة تعرض **اسم الدخول الإنجليزي** المسجّل للموظف، مع الحالة الإنجليزية؛ اسم الموظف العربي الكامل يظهر في المنصة والتطبيق. لو مطلوب عربي كامل على الجهاز، يلزم شاشة تدعم رسم خط عربي وتعديل العرض.

## 4. إعداد كل قارئ قبل الرفع

يوجد بالفعل قارئ مستقل لكل فرع على قاعدة البيانات، وله DEVICE_ID وDEVICE_TOKEN خاصان. الملفات الخاصة خارج مجلد OneDrive والمستودع:

```text
C:\Users\abdol\AppData\Local\JoeStore\Attendance\ReaderConfigs\branch1.h
C:\Users\abdol\AppData\Local\JoeStore\Attendance\ReaderConfigs\branch2.h
```

افتح ملف الفرع الذي تبرمجه وعدّل `WIFI_SSID` و`WIFI_PASSWORD` لشبكة **2.4GHz**. اترك هوية القارئ ومفتاحه كما هما. عنوان API مضبوط على Vercel. إذا احتجت تغيير مفتاح، استخدم «إصدار مفتاح بديل» من لوحة الأدمين وحدّث الملف الخاص؛ المفتاح القديم يتوقف فورًا.

لا تضع مفاتيح القارئ في Git أو صورة أو رسالة عامة. ملف `attendance-config.h` الذي تنشئه أداة الرفع مستثنى من Git، لكنه يحتوي المفتاح؛ لا تشاركه.

## 5. رفع الكود

1. وصّل **جهازًا واحدًا فقط** بكابل USB يدعم نقل البيانات.
2. افتح Device Manager → Ports وسجّل منفذ CP210x/CH340 المناسب. منافذ Bluetooth ليست منفذ ESP32.
3. افتح PowerShell داخل مجلد المشروع، واستبدل COM7 بمنفذك الحقيقي:

```powershell
Set-Location -LiteralPath 'C:\Users\abdol\OneDrive\Desktop\task\atendance_system'
.\scripts\flash-reader.ps1 -Branch branch1 -Port COM7 -Lcd i2c
```

وللقارئ الثاني، إذا شاشته العادية:

```powershell
.\scripts\flash-reader.ps1 -Branch branch2 -Port COM8 -Lcd parallel
```

الأداة تستخدم PlatformIO الموجود في `.tools`، تنسخ إعداد الفرع الخاص، تبني الكود وتفلشه. إذا علقت عند Connecting اضغط BOOT أثناء الاتصال ثم اتركه. تأكد من الكابل والمنفذ إذا لم يظهر الجهاز.

افتح Serial Monitor عند 115200:

```powershell
& .\.tools\pio-runtime\Scripts\python.exe -m platformio device monitor -p COM7 -b 115200
```

انتظر `Clock synchronized from Internet` قبل الاستخدام الطبيعي. لو ظهر `RC522 not detected` راجع تغذيته وSPI. لو ظهر `LCD I2C not found` راجع العنوان والمحوّل والأرضي. الشاشة غير المكتشفة لا تمنع تسجيل القراءات.

**تهيئة التخزين لأول جهاز جديد فقط:** إذا ظهر `LittleFS unavailable` والجهاز جديد ولا توجد عليه أي قراءات لازمة، أرسل `--format` ثم Enter من Serial Monitor. الأمر يمسح الطابور؛ لا تستخدمه لعلاج انقطاع الإنترنت أو على جهاز عليه قراءات غير مرفوعة. الكود لا يهيئ التخزين تلقائيًا.

## 6. الفلو المسجّل على المنصة

مثال: يوم العمل 10:00، شيفت 12:00–21:00، وفتح الانصراف قبل النهاية بـ60 دقيقة:

| القراءة | النتيجة |
|---|---|
| أول قراءة بعد 10:00، حتى لو متأخر بعد 20:00 | حضور |
| قراءة إضافية قبل 20:00 | حركة / REFRESH |
| إعادة مسح سريعة خلال 30 ثانية من الحضور | REFRESH؛ تمنع انصرافًا بالخطأ |
| أول قراءة بعد 20:00 وبعد المهلة | انصراف |
| قراءة بعد الانصراف في نفس يوم العمل | REFRESH بعد الانصراف، لا حضور ثانٍ |
| أول قراءة بعد بداية يوم العمل التالي | حضور جديد |

الأدمين يغيّر بداية اليوم والحد الأقصى العام ومهلة المسح من الإعدادات. من بروفايل الموظف يغيّر الشيفت، وفتح الحضور، وفتح الانصراف بساعة محددة أو مهلة قبل نهاية الشيفت، والحد الأقصى الخاص به. القيمة الافتراضية للحد الأقصى **12 ساعة**. القراءات تحفظ قواعدها حسب وقت الالتقاط؛ تغيير القواعد لا يعيد تصنيف حركة قديمة إلى انصراف. تغيير بداية اليوم لا ينقل اليوم الجاري أو التقارير القديمة.

إذا نسي الانصراف: يتوقف GPS عند الحد الأقصى وتظهر «انصراف ناقص»، ولا يخترع النظام انصرافًا. يمكن للمدير تصحيح القراءة مع سبب وسجل مراجعة. بداية حضور جديد تنهي فترة التتبع المفتوحة السابقة لمنع تداخل حساب الوقت.

## 7. الهاتف والتحقق من الوجود

ثبّت APK الجديد على Android وسجّل دخول الموظف، وافتح التطبيق قبل أول مسح، ثم اضغط «تجهيز متابعة الموقع بعد حضور الكارت» واسمح بالموقع الدقيق وإشعار الخدمة. يراقب التطبيق **حالة الكارت فقط** قبل الحضور؛ GPS يبدأ بعد وصول حضور الكارت للسيرفر وتحديث الهاتف (عادة دورة التحديث 15 ثانية، ثم وقت التقاط GPS).

بعد الانصراف يتوقف عندما تصله الحالة أو عند الحد الأقصى المحفوظ. إذا الهاتف Offline فلن يعرف الانصراف الجديد حتى يعود الاتصال؛ قد يستمر الجمع المحلي حتى الحد المحفوظ، لكن السيرفر يستبعد العينات الملتقطة بعد الانصراف. تعديل الحد يحتاج وصول تحديثه للهاتف، وإلا يبقى الحد المحفوظ نافذًا. هذه نقطة تُفحص في الاختبار.

على iPhone يحتاج التطبيق صلاحية «دائمًا» والموقع الدقيق، ويجب فتحه عند الحضور. نظام iOS لا يضمن إيقاظ التطبيق من الكارت عن بُعد، خصوصًا بعد إغلاقه بالقوة. الكود يُبنى لمحاكي iOS، لكن تركيب نسخة دائمة على iPhone / TestFlight يحتاج ترتيبات Apple Developer والتوقيع؛ لا يوجد حاليًا حساب مطوّر مدفوع حسب المعلومات المتاحة. لا تعتبر اختبار المحاكي اختبار GPS خلفية على iPhone حقيقي.

كل GPS يُصنّف: داخل فرع، خارج الفروع (أحمر)، أو غير معلوم (دقة ضعيفة أو فجوة). نصف قطر كل فرع 20 مترًا؛ الدقة لازم تسمح بالتأكيد داخل هذا النطاق. سجل الكارت وحده لا يمنح وقتًا مؤكدًا داخل الفرع، ولا تشغيل التطبيق وحده يسجّل حضورًا.

## 8. الاختبار اليدوي على Vercel

استخدم حساب موظف اختبار مستقل، أنشئه من لوحة الأدمين، وكارت اختبار مربوطًا به؛ لا تغيّر شيفت موظف حقيقي من أجل التجربة. اجعل تاريخ بداية متابعة حساب الاختبار لا يتجاوز يوم شيفته الجاري، خصوصًا لو التجربة بعد منتصف الليل وقبل بداية يوم العمل الجديد. اختبر كل قارئ وشاشة على حدة ثم الاثنين معًا.

APK التجربة إصدار 1.1.0، مبني بمفتاح debug المحلي الموجود على هذا الكمبيوتر. إذا كنت تستخدم نسخة سابقة موقّعة بمفتاح مختلف فقد يرفض Android تحديثها. **لا تحذف التطبيق أو بياناته بينما توجد أحداث غير مرفوعة**؛ زامنها أولًا أو جهّز تحديثًا بنفس مفتاح النسخة المثبتة. النسخة التجريبية ليست إصدارًا منشورًا على متجر التطبيقات.

1. **التوصيل:** شاشة تبدأ، RC522 يظهر في Serial، Wi‑Fi والساعة جاهزان، ووقت آخر اتصال يتحدث في لوحة «الكروت وقارئات الفروع» بعد إرسال قراءة.
2. **الربط:** امسح كارتًا غير مربوط؛ يظهر UID و«كارت غير مربوط». من الأدمين اربطه بحساب الاختبار، ثم امسحه مجددًا. لا يلزم كتابة اسم الموظف على ذاكرة الكارت.
3. **قبل الحضور:** فعّل متابعة الهاتف؛ يجب ألا يجمع GPS قبل أول حضور، ولا توجد نافذة GPS مفتوحة على السيرفر.
4. **الحضور:** أول مسح يعرض اسم الدخول و`IN / GPS PENDING` بعد ACK. تأكد أن وقت الحضور هو وقت المسح وأن GPS يصل بعدها ويظهر موقعًا دقيقًا.
5. **Refresh:** ارفع الكارت عن القارئ ثم امسحه ثانية قبل فتح الانصراف؛ الشاشة `REFRESH`، ووقت أول الحضور ثابت. إبقاؤه على القارئ لا يرسل سيلًا من القراءات.
6. **التنقل:** امسح نفس الكارت بقارئ الفرع الثاني؛ Refresh من القارئ الثاني، ويظهر انتقال الفرع من GPS الفعلي. قراءة الفرع لا تُعتبر دليل موقع الهاتف.
7. **كارت مع زميل:** اجعل صاحب هاتف الاختبار خارج نطاق الفرعين مع GPS مفعّل، وامسح الكارت داخل الفرع؛ الكارت مسجّل ولكن إحداثيات الموظف «خارج الفروع» باللون الأحمر، ولا يتحول الوقت الخارجي إلى حضور مؤكد.
8. **انصراف:** افتح وقت الانصراف الآن لحساب الاختبار من بروفايله، وانتظر مهلة منع المسح السريع، ثم امسح؛ الشاشة `CHECK OUT`، ثم يتوقف GPS عند وصول الحالة. مسح آخر لا يبدأ حضورًا ثانيًا.
9. **انقطاع إنترنت القارئ:** اقطع اتصال القارئ بالشبكة مع إبقاء الكهرباء؛ امسح كارت اختبار، ثم أعد الشبكة. كل قراءة محفوظة بوقتها الأصلي، ولا تُحذف إلا بعد ACK. الحالة على الشاشة تنتظر ردّ السيرفر. اختبر إعادة تشغيل القارئ والطابور ما زال موجودًا ثم عودة النت.
10. **انقطاع إنترنت الهاتف:** بعد حضور مؤكد قطع Wi‑Fi/بيانات الهاتف مع بقاء GPS؛ العداد يزيد محليًا. أعد الإنترنت؛ يتفرغ الطابور بلا تكرار، وتظل أوقات الالتقاط كما هي. الانصراف أثناء Offline يخضع للحد المحفوظ كما توضّح الخطوة السابقة.
11. **حد الساعات:** في حساب اختبار مستقل، اجعل الحد ساعة واحدة، اتركه بلا انصراف؛ بعد ساعة يقف GPS وتظهر «انصراف ناقص». لا تُقصر حد موظف حقيقي من أجل الاختبار.
12. **التقرير:** الأدمين → التقارير → «تقرير نهاية يوم العمل». يظهر آخر يوم انتهى تلقائيًا، أو اختر يوم الاختبار؛ راجع فترة الكارت، الوقت داخل كل فرع، خارج الفروع، غير المعلوم، ونسبة الوقت في الأماكن. الفترة المفتوحة تظل مبدئية، والمزامنة المتأخرة تعدّل التقرير.
13. **حساب اليوم التالي / شيفت عبر منتصف الليل:** جرّبه في حساب اختبار يومين متتاليين؛ الساعة 00:00 ليست بداية يوم جديد ما دام حد اليوم 10:00. يجب ألا يبدأ حضورًا ثانيًا قبل الحد الجديد.
14. **قفل الشاشة:** جرّب الهاتف الحقيقي وهو مقفول مدة 15 دقيقة داخل فترة حضور، ثم افتحه وراجع timestamps والإحداثيات. أعد تجربة إغلاق التطبيق بالقوة؛ يجب أن تظهر الفجوة ولا يحتسبها وجودًا داخل الفرع.

غياب GPS أو رفض الصلاحية أو خروج صاحب الهاتف ليس «داخل الفرع». لا تقدر جولة API أو نجاح Compile تثبت الكهرباء والهوائي والشاشة أو تشغيل GPS في خلفية الهاتف؛ هذه اختبارات فعلية على الأجهزة المطلوبة أعلاه.

## ملفات الكود

- `src/main.cpp`: قراءة RC522، حفظ LittleFS، HTTPS وACK، وحالات الشاشة.
- `include/display.h`: نفس واجهة العرض مع تنفيذ I²C أو parallel.
- `include/config.example.h`: إعداد غير سري كنموذج.
- `../../scripts/flash-reader.ps1`: اختيار الفرع والمنفذ والشاشة والرفع.
- `../../scripts/verify-daily-flow-production.mjs`: اختبارات تكامل على Vercel بموظفين وقارئات مؤقتة؛ تُنظّف بياناتها فقط.
