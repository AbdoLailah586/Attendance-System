# حضور جو ستور

إدارة حضور موظفي المحلات والفروع بالكروت، ومتابعة GPS داخل الشيفت فقط، مع لوحة مدير على الويب وتطبيق Capacitor لـ Android وiPhone.

الموقع الأساسي: https://attendance-system-joe-2026.vercel.app

## ما تم تنفيذه

- الحضور والانصراف من قارئ الكارت في كل فرع. أزرار الهاتف تفعّل وتوقف GPS فقط؛ فتح الصفحة لا ينشئ حضورًا.
- أجهزة ESP32 ترفع قراءات RDM6300 عبر HTTPS بمفتاح خاص لكل قارئ، وتخزنها في LittleFS وقت انقطاع الشبكة. [التجميع والقطع والتوصيلات](firmware/esp32-reader/README.md).
- النسخة النهائية للقارئ تعمل بتغذية USB وWi‑Fi مستمرين دون ساعة خارجية؛ تضبط الوقت من الإنترنت عند الإقلاع. إعادة التشغيل دون إنترنت تحفظ القراءات الجديدة بوقت غير معلوم للمراجعة.
- لوحة المدير تربط الكروت بالموظفين، تعطّل القارئ أو الكارت، تراجع القراءات وتصنّفها، وتحفظ تاريخ تعديلات القراءة.
- حفظ أحداث الويب في IndexedDB قبل إرسالها، ومزامنتها عند عودة الاتصال أو فتح الصفحة.
- أحداث تحمل UUID ووقت التقاط مستقلًا عن وقت وصولها. إعادة الإرسال لا تكرر سجلات الحضور.
- حفظ أصلي في تطبيق الهاتف: SQLite على Android، وملف ذري محمي على iOS، مع حفظ الجلسة في Android Keystore وApple Keychain.
- خدمة موقع ظاهرة بإشعار أثناء الشيفت على Android، وCore Location في الخلفية على iOS.
- إعادة محاولة إرسال الأحداث في الخلفية عبر WorkManager على Android وBGTaskScheduler على iOS، حتى عند انتهاء الشيفت بدون إنترنت. توقيت مهام الخلفية يحدده نظام الهاتف؛ فتح التطبيق أو عودة عينات الموقع يتيح محاولة فورية.
- اختيار مواقع الفروع على الخريطة، إضافة فروع، فتح موقع الفرع في Google Maps، واستخدام رابط Google Maps كامل بإحداثيات.
- لوحة أدمين لمتابعة الموظفين، سجل أحداث قابل للتصفح، تقارير، وتصدير CSV.
- حساب وقت الحضور داخل الفروع، الخروج، الإضافي بعد نهاية الشيفت، الانصراف المبكر، وفجوات التتبع.
- الحسابات تستخدم `Africa/Cairo` بما فيه التوقيت الصيفي والشيفتات التي تعبر منتصف الليل.
- إيقاف مولد البيانات التجريبية؛ تعطيل الموظف يحتفظ بسجل حضوره، وكلمات المرور لا تُعرض في API.

## قواعد الحساب

تقارير الإدارة تدعم يومًا محددًا، أسبوعًا من تاريخ البداية (7 أيام)، دورة شهر خاصة بكل موظف، وفترة مخصصة حتى 366 يومًا شاملة البداية والنهاية. كل تقرير يعرض أيام الحضور والغياب والراحة والتأخير، دقائق التأخير، إجمالي التواجد، وقت كل فرع، الإضافي والخروج وفجوات GPS؛ مع تفاصيل الأيام والحركة وتصدير ملخص أو تفاصيل CSV.

من «إدارة حسابات الموظفين ← تعديل» يمكن تغيير الاسم، اسم الدخول، الهاتف، كلمة المرور، الصلاحية، حالة الحساب، مواعيد الشيفت، فترة السماح، أيام العمل، يوم بداية الدورة، وبداية المتابعة. تغييرات قواعد العمل تحمل تاريخ سريان ولا تستبدل حساب الأيام الأقدم؛ اختيار تاريخ سريان سابق يعيد حساب الفترة المقصودة. لا يمكن تعطيل آخر مدير نشط. الغياب لا يُحسب قبل نهاية الشيفت، أو في أيام الراحة والمستقبل وما قبل بداية المتابعة. الدورة التي تبدأ يوم 29–31 تستخدم آخر يوم متاح في الأشهر الأقصر.

التصفير المصرح به يستخدم `scripts/reset-production-attendance.mjs --execute` مع متغيرات البيئة الخاصة بقاعدة الكلاود وحساب المدير. يحفظ نسخة خاصة من السجل في `private_attendance_archive` ثم يمسح السجل النشط وحسابات QA المميزة، ويضع وقت بداية جديدًا. الأحداث القديمة التي تصل لاحقًا تُقرّ كأحداث مستبعدة بسبب التصفير، ولا ترجع للتقارير. مواقع الفروع وحسابات الدخول الفعلية تبقى محفوظة. لا تشغّل سكريبت التصفير دون طلب صريح من المالك.

الحضور الأساسي يُحسب من توقيتَي الكارت المرتبطين بيوم بداية الشيفت، بما فيه الشيفت العابر لمنتصف الليل. الشيفت المفتوح بدون انصراف يعرض ساعات مبدئية ولا يخترع انصرافًا أو يعتمد إجمالي ساعات نهائيًا. الموقع يُستخدم لمتابعة الخروج داخل أيام ومواعيد العمل فقط؛ فجوات GPS لا تلغي حضور الكارت، ولا تُنسب لفرع مفترض. وقت الفرعين والخروج وفجوات التتبع منفصلة عن إجمالي مدة الكارت. الإضافي هو الوقت المسجل بالكارت بعد نهاية الشيفت، وليس موافقة صرف مالي. النوافذ الافتراضية للحضور 60 دقيقة قبل البداية و120 بعدها، وللانصراف 60 قبل النهاية و180 بعدها، وقابلة للتعديل لكل موظف. القراءات خارجها أو المتداخلة تتطلب مراجعة إدارية.

جدول 7 أيام يُحفظ على الهاتف لاستكمال المتابعة وقت انقطاع الشبكة. خارج المواعيد أو بعد انتهاء صلاحية الجدول يتوقف GPS، والسيرفر يرفض عينات خارج الشيفت وأحداث الحضور اليدوية القديمة. الوصول لانصراف الكارت يوقف المتابعة مبكرًا. Android يحتفظ بخدمة جدول ظاهرة؛ على iPhone افتح التطبيق وفعّل المتابعة عند بداية الشيفت لأن نظام iOS لا يضمن إيقاظ التطبيق المغلق كل يوم.

التتبع يستمر أثناء الشيفت. صلاحيات الموقع، إيقاف التطبيق إجباريًا، إعادة تشغيل الهاتف، وضع الطاقة، وتوفر GPS تؤثر على جمع العينات. لا يمكن ضمان عينة كل دقيقة تحت كل ظروف النظام. بعد إغلاق التطبيق إجباريًا أو إعادة التشغيل يجب فتحه لاستكمال التتبع. واجهة الويب/PWA تجمع الموقع أثناء عملها في المتصفح؛ التتبع مع قفل الشاشة يحتاج تطبيق الهاتف.

السجلات القديمة بدون UUID تظل مقروءة بالقواعد التاريخية، ولا يتم حذفها. وقت استلام السجلات القديمة يُملأ بوقت الحدث أثناء ترقية الجدول لأنه لم يكن مسجلًا سابقًا.

## إعداد الويب

Next.js 16.3، React 19، TypeScript، PostgreSQL/Neon، Leaflet.

متغيرات Vercel المطلوبة:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST/attendance_db?sslmode=require
JWT_SECRET=generate_a_random_secret_of_at_least_32_bytes
```

استخدم أسرارًا فعلية في Vercel، ولا تضعها في Git. التعديلات على الجداول تُطبّق تلقائيًا بشكل إضافي عند أول استخدام؛ لا تشغّل `scripts/init-db.mjs` على قاعدة قائمة. ملف التهيئة مخصص لقاعدة جديدة فقط.

فحوص التجميع:

```powershell
npm ci
npm run lint
npm run build
```

## تطبيق الهاتف

الكود في `mobile/`. الواجهة مضمّنة داخل التطبيق ويمكن فتحها بدون إنترنت بعد تسجيل الدخول أول مرة. اتصالاته تشير إلى دومين Vercel الأساسي، دون عنوان تطوير محلي.

```powershell
cd mobile
npm ci
npm run sync
```

Android يحتاج JDK 21 وSDK 36. ملف `mobile/android/local.properties` يحدد مسار SDK على جهاز البناء. البناء:

```powershell
cd android
.\gradlew.bat assembleDebug
```

الـ APK التجريبي: `mobile/android/app/build/outputs/apk/debug/app-debug.apk`. نسخة التوزيع تحتاج مفتاح توقيع Release خاص بالمالك.

iPhone يحتاج Mac وXcode وحساب Apple Developer لتوقيع نسخة تعمل على الأجهزة أو توزيعها عبر TestFlight. افتح `mobile/ios/App/App.xcodeproj`، اختر فريق التوقيع، وفعّل صلاحية الموقع «دائمًا» على الهاتف. إعدادات الخلفية والخصوصية موجودة بالمشروع. يوجد workflow يدوي في GitHub يبني Android ونسخة iOS Simulator بدون توقيع؛ نجاح بناء Simulator لا يؤكد عمل GPS على جهاز حقيقي.

## اختبارات التشغيل على Vercel

الفحوص الروتينية بعد بداية الاستخدام الحقيقي: `node scripts/verify-period-reports.mjs` للأنواع الأربعة دون إنشاء أي بيانات. فحص الحالة الصفرية بعد التصفير: `node scripts/verify-reset.mjs`. الاختبارات التاريخية التي تنشئ بيانات QA تتطلب `--write-test-events` ولا تعمل بعد وضع وقت التصفير الفعلي؛ النتائج التي أُنجزت قبل التصفير محفوظة في `artifacts/period-report-verification.json`، وكل حسابات وأحداث تلك الاختبارات أُزيلت من السجل النشط.

السكريبت يرفض استخدام localhost أو Preview. استخدم حساب أدمين من متغيرات البيئة دون حفظ كلمة مروره في التقارير:

```powershell
$env:QA_ADMIN_USERNAME='your_admin_username'
$env:QA_ADMIN_PASSWORD='your_admin_password'
node scripts/verify-production.mjs
node scripts/verify-production.mjs --write-test-events
```

الوضع الثاني ينشئ حساب QA مستقلًا ويسجل أحداثًا اصطناعية باسم واضح، ثم يعطله ويحتفظ بالسجل. لا يمسح سجلات الموظفين ولا يغير أماكن الفروع. يختبر حفظ وقت الحدث، منع التكرار، الصلاحيات، حساب الخروج والإضافي، والسجل الإداري. نتيجة التنفيذ تُكتب في `artifacts/production-verification.json`.

اختبار ميداني مطلوب على Android وiPhone: قفل الشاشة أثناء شيفت، قطع الإنترنت، الانتقال بين الفرعين والخروج منهما، إعادة الاتصال والتحقق من ظهور نفس الأحداث والتوقيت في لوحة Vercel. مراجعة الإضافي تعتمد على قواعد الشيفت التي يحددها المدير.
